# 世界スタジアム/アリーナ図鑑サイト — Phase 1: データ収集パイプライン 設計

## プロジェクト全体のビジョン

世界中のスタジアム・アリーナなどのスポーツ施設を、地球儀を旅するようなUIで閲覧できるサイトを作る。

- 完全無料で運用する
- 地球儀のようなUI/UXでworldmapを旅する感覚を提供する(表示テーマを複数用意し切り替え可能にする: A.リアル衛星写真風 / B.フラット・ローポリ / C.ダーク×データビジュアライゼーション風)
- 施設情報はできるだけ細かく大量に(将来的には歴史・改修履歴・イベント履歴・周辺交通アクセスまで)
- 出典を確実に明示する

対象範囲は世界中の全種目・全施設(数千〜数万件規模)。プロジェクトは以下のサブプロジェクトに分解し、順に進める。

- **Phase 1(本spec)**: データ収集パイプライン — Wikidataから施設の基本情報を自動収集し、静的JSONとして生成する
- **Phase 2**: 地球儀UI — Phase 1のJSONを読み込み、地球儀上に施設をマーカー表示し、詳細ページと出典一覧を表示する。表示テーマ切り替え機能を含む
- **Phase 3**: 拡張 — 検索/フィルター、Wikipedia本文からの歴史・改修履歴等の抽出、OpenStreetMap併用による施設カバレッジ拡大

## Phase 1 のスコープ

Wikidataから世界中のスタジアム/アリーナ等の基本属性を自動収集し、静的JSONファイルとして生成・維持する仕組みを作る。DBやサーバーサイドアプリケーションは持たない。

### 技術構成

- ホスティング: **GitHub Pages**(静的サイトとして将来Phase 2のHTML/JSを配置)
- データ収集・更新: **GitHub Actions**(スケジュール実行のワークフロー)
- データ保存先: リポジトリ内の**静的JSONファイル**(DB・外部サーバーは使用しない)
- Vercel / Supabase / Xサーバーは使用しない

### アーキテクチャ

```
Wikidata SPARQL Query Service
        │ (施設一覧+基本属性を取得)
        ▼
収集スクリプト (Node.js, scripts/collect-facilities.js)
        │ 正規化・マージ
        ▼
data/facilities/*.json  (地域 or 種目単位で分割)
data/sync_log.json      (直近の実行結果)
        │
        ▼
GitHub Actions が変更をリポジトリにコミット
```

Phase 2以降、GitHub PagesがこのリポジトリのHTML/JS/JSONをそのまま配信する想定。

### データモデル(JSON構造)

`data/facilities/<region-or-key>.json` に施設単位のレコード配列を保存する。

```json
{
  "id": "Q123456",           // WikidataのQID
  "name": "施設名(英語/現地語)",
  "name_ja": "施設名(日本語、あれば)",
  "lat": 35.0,
  "lng": 139.0,
  "country": "JP",
  "sport_types": ["football"],
  "capacity": 50000,
  "opened_year": 1990,
  "closed_year": null,
  "roof_type": null,
  "teams": ["チーム名"],
  "wikipedia_url": "https://ja.wikipedia.org/wiki/...",
  "wikidata_url": "https://www.wikidata.org/wiki/Q123456",
  "image_url": null,
  "sources": ["Wikidata", "Wikipedia"],
  "last_synced_at": "2026-09-08T00:00:00Z"
}
```

座標(lat/lng)を持たないエンティティは対象外とする(地球儀に配置できないため必須項目)。それ以外の項目は欠損を許容し、取得できたものだけ埋める。

`data/facility_details/` は将来のPhase 3(Wikipedia本文からの歴史・改修履歴抽出)の受け皿として、空のディレクトリ構成だけ先に用意しておく。

### 収集ロジック

- SPARQLで `instance of`(P31)がスタジアム/アリーナ/競技場などスポーツ施設系のクラスに該当し、かつ座標(P625)を持つエンティティを対象にする
- 1回のクエリで数万件を取得しようとするとタイムアウトするため、**国別または種目別に分割**してページング取得する
- Wikipedia記事URLはWikidataのsitelinksから**日本語→英語**の優先順で取得する
- 取得した属性を上記JSON構造に正規化し、既存ファイルとマージ(同一QIDは上書き更新)

### 実行方式

- **初回一括投入**: GitHub Actionsのワークフローを手動トリガーで一度実行し、全件を投入する
- **定期更新**: GitHub Actionsのスケジュール実行(1日1回)で、新規追加・値の変更があった分だけ差分反映する
- 更新があった場合のみ `data/` 配下の変更をコミットする(変更がなければコミットしない)

### エラーハンドリング

- SPARQLのレート制限・タイムアウトはリトライ+指数バックオフで対応する
- 個別クエリが失敗しても他の分割クエリの処理は継続し、失敗した範囲は次回実行時に再試行する
- 実行結果(取得件数・成功/失敗件数・実行日時)を `data/sync_log.json` に追記する

### テスト方針

- SPARQLレスポンス→JSONレコードへの変換ロジックに対するユニットテストを用意する(サンプルレスポンスを使い、必須項目の欠落時の挙動や重複QIDのマージを検証する)
- GitHub Actionsのワークフロー自体は手動トリガーで少数件のドライランを行い、実データでの動作を確認する

## Phase 1 のスコープ外

- 地球儀UIやWebページの実装(Phase 2)
- Wikipedia本文の歴史・改修履歴・イベント履歴の抽出(Phase 3)
- OpenStreetMap併用によるデータ補完(Phase 3)
- 検索・フィルター機能(Phase 3)
- 出典の個別項目表示(Phase 2でページ下部にまとめて出典一覧を表示する方針。データ構造には`sources`フィールドとして保持しておく)
